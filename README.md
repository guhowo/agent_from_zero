# agent_from_zero

## planning
### 为什么需要planning
LLM所谓的planning能力
llm本身也有所谓的planning能力，llm收到用户输入和prompt后会ReAct、CoT 等方式边想边做，根据每一步返回的结果进行调整，LLM的planning能力是implicit的，即llm会自己决定如何规划，但有时需要显式地告诉llm如何规划，这时就需要planning。
prompt能解决planning问题吗？
开发者通过详细的prompt来指导llm如何规划，适合步骤少且固定，工具输出稳定，且每步输出可以校验的情况。但是不能根治漏步、跳步、顺序错、合并步骤等问题。原因主要如下：
1. prompt的长度有限制，步骤太多会超出token限制
2. 长 prompt 注意力稀释：步骤越多，越容易遗忘或冲突。
3. 错误会累积：第一步出错，后面全错。
4. 格式正确 ≠ 语义正确
5. 提示注入：用户输入或工具返回可能覆盖你的“严格步骤”。
   **结论**：严格 prompt 可以降低随机性，但不能解决随机性。
   如何解决？
1. 与 ReAct 模式“边想边做”不同，而是采用Plan-and-Execute模式，先规划后执行
   * Planner（规划器）：接收原始任务，调用 LLM 生成一个结构化的步骤列表（Plan）。这个列表可以是简单的字符串数组，也可以是包含依赖关系的 DAG（有向无环图）
   * Executor（执行器）：按顺序（或依赖关系）逐一执行计划中的步骤。每个步骤的执行结果会被记录到状态中。
   * Replanner（重规划器）：这是 P-t-E 模式实现“韧性”的关键。每步执行后，控制流会进入 Replanner 节点。它会综合原始目标、原计划、以及所有已执行步骤及其结果，判断下一步该做什么：继续执行、生成新计划、或宣布任务完成。
